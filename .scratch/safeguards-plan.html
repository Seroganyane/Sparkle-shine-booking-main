01 User typing limits

Every field that accepts free text or a number has an upper bound, chosen for a reason — never a round number picked at random. Two mechanisms do the bounding together: the HTML field itself refuses further keystrokes (so a limit is felt immediately, not discovered after submitting), and a schema re‑checks the same limit before anything is sent to the server, since a typed limit can be bypassed by anyone calling the API directly. Where the valid values are a small fixed set — a wash bay, a package, a reward count — the interface uses a picker or a number spinner instead of a character limit, which removes invalid input entirely rather than merely bounding it.

02 Error trapping & prevention

No single check is trusted alone. The same rule is often enforced two or three times on purpose — in the browser for instant feedback, and again on the server because the browser can always be bypassed by anyone who calls the API directly. Reading top to bottom, each layer below catches what the one before it missed.

1

Make the mistake impossible to type

Digit‑only fields strip anything else as it's typed (invitation code, identity number); small fixed choices are buttons or spinners, not text, so there's no invalid string to even enter (wash bay, package, reward count).

Example: the identity‑number box calls e.target.value.replace(/\D/g, "") on every keystroke — a letter never appears in the field at all.
2

Validate before any network call

Zod schemas run a full safeParse on submit. A failure never produces a generic message — showFieldError() shows the exact reason and returns keyboard focus to the one field that needs fixing, even after the toast closes.

Example: src/lib/fieldError.ts pairs toast.error() with document.getElementById(fieldId)?.focus() via queueMicrotask.
3

Catch every network call and translate the failure

Every submit handler wraps its Supabase and edge‑function calls in try/catch, so a failure always becomes a readable toast — never a blank screen or a silent, unhandled rejection.

Example: src/lib/edgeFunctionError.ts unwraps the JSON body an edge function returned (with its own inner try/catch for gateway responses that aren't JSON at all), so the user sees "this invitation has expired" instead of "non‑2xx status code."
4

The server is the real authority, never the UI

Row‑level security policies are the actual gatekeeper on every table — a customer's own browser sending a forged request still cannot touch someone else's booking. Security‑definer database functions re‑run the business rule server‑side even though the client already checked it.

Example: accept_employee_booking, verify_employee_vehicle, report_vehicle_mismatch, consume_staff_invitation and is_valid_sa_id_number all re‑check their own precondition inside the database, independent of what the browser already validated.
5

Races are caught by the database, not assumed away

Two unique constraints make certain conflicts physically impossible even if two people act at the same instant, and the app recognises that specific database error and turns it into a plain‑language retry — not a raw error code.

Example: one_active_booking_per_slot and one_active_assignment_per_employee reject a second write outright; the booking dialog catches Postgres error 23505 and shows "that wash bay was just taken — please choose a different slot."
6

A catch‑all for anything that still slips through

ErrorBoundary.tsx wraps the entire app. Any rendering‑time exception is logged in full for developers, while the person using the app only ever sees a calm recovery screen with "Reload" and "Go home" — never a raw stack trace.

Fixed this pass: the fallback used to print the raw JavaScript error object straight onto the page.
7

Routing and authorization edge cases

ProtectedRoute.tsx distinguishes "still checking," "not signed in" and "signed in with the wrong role" — each gets its own correct outcome, never a flash of the wrong page. NotFound.tsx catches any URL that doesn't exist.

03 What happens when the user does something unexpected

Each row names a specific way a real person can go off the expected path, and exactly what the system does about it — grounded in the code, not a hypothetical.

Does
Double‑clicks "Book," "Send invitation," or "Confirm"
Result
Only one request is ever sent
Why
The button disables itself the instant a request starts (disabled={loading} everywhere). If two tabs still raced, the new unique index rejects the second write.
Does
Pastes a huge block of text into "car make" or a chat message
Result
Nothing past the limit is ever typed
Why
The field's own maxLength stops accepting characters — nothing is silently cut off after the fact.
Does
Leaves a required field blank and submits anyway
Result
A specific, field‑targeted message, focus returned
Why
HTML required blocks it first; Zod's safeParse is the real backstop if that's ever bypassed (e.g. a programmatic submit).
Does
Types letters into a digits‑only field (invitation code, ID number)
Result
The letter never appears in the box
Why
Non‑digit characters are stripped on every keystroke, before the field re‑renders.
Does
Picks a wash bay someone else takes a second before submitting
Result
Clear retry message, slot list reloaded
Why
Availability comes from a live, realtime‑subscribed check; if they still race, the database's unique index refuses the second insert and the UI explains why.
Does
Rambles a long, run‑on sentence to the voice assistant
Result
Truncated to 200 characters, conversation stays on track
Why
The cap is applied in code twice — right where the transcript is captured, and again inside the shared message handler.
Does
Says something the chatbot can't parse (garbled package name, no digits for a slot)
Result
It asks again with a clarifying example
Why
Fixed this pass — an unrecognised package name used to silently become "Premium" without telling the customer. It now stays on the same question instead of guessing.
Does
Photographs the wrong thing for the plate scanner
Result
"Could not be read" / "does not match," with Retake and Report options
Why
OCR text that doesn't match the expected plate is never treated as a match — staff get an explicit choice, never a silent guess.
Does
Loses network connection mid‑submit
Result
A clear error toast; the form keeps its contents; button re‑enabled
Why
try/catch/finally around every request — finally always turns "loading" back off so the person can just retry.
Does
Loses staff/admin rights mid‑session (e.g. an admin demotes them while they're still using the app)
Result
The next write fails cleanly with a toast, not a silent success
Why
Row‑level security is checked at the database on every request — a stale client session can't act on permissions it no longer holds.
Does
Refreshes or navigates away mid‑signup
Result
Name, username, email and phone are restored automatically
Why
The signup draft (never the password) is kept in sessionStorage and reloaded when the form mounts again.
Does
Pastes script tags or SQL‑looking text into a name field
Result
Stored and displayed as inert text — nothing executes
Why
React escapes all rendered text by default (no raw‑HTML injection anywhere in these forms), and every write goes through Supabase's parameterised query builder, never hand‑built SQL.
Does
Visits a URL that doesn't exist, or one they're not allowed to see
Result
A proper 404, or a redirect to their own real home page
Why
NotFound.tsx catches unknown routes; ProtectedRoute.tsx sends a signed‑out visitor to /auth and a signed‑in visitor with the wrong role to their dashboard, never an error screen.
Does
Triggers a genuinely unforeseen bug somewhere in the interface
Result
A calm recovery screen — "Reload" or "Go home" — instead of a blank page
Why
ErrorBoundary.tsx catches it at the top of the app and logs full technical detail for developers, never showing that detail to the person using the app.

Known gaps & recommended follow‑ups

Named on purpose rather than left implicit — a plan that only lists what's covered isn't trustworthy about what isn't.

Gap
Free‑text database columns have no hard length ceiling. Car details, notes, names and notification text are stored as unbounded text columns — only the browser and Zod enforce a limit, so a request made directly against the API (bypassing the web app entirely) could still write an arbitrarily long value. Recommendation: add CHECK (char_length(...) <= N) constraints on the highest‑traffic columns, the same way the identity‑number format is already enforced at the database level.
Gap
Two unreachable legacy pages remain in the codebase. AdminLogin.tsx and EmployeeLogin.tsx still exist with their own, separately‑drifted validation, even though both routes now just redirect to /auth. Recommendation: remove them so there's only one sign‑in implementation to keep correct.
Gap
Stock deduction on a paid order is intentionally best‑effort. If it fails, the payment still succeeds and the failure is only logged server‑side — the right call so a stock bug never blocks a sale, but it means stock and orders could rarely drift out of sync without an admin noticing. Recommendation: a small admin‑visible reconciliation view if stock accuracy becomes critical at scale.
